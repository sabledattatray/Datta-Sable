# Phase 4 — Razorpay test integration

Reuses `lib/commerce/payments.ts`, SDK, serializable capture transaction, webhook queue and refund processor. No second payment model. Server reads DB price; order/item snapshots use integer paise; first handbook is 9900 INR. Product checks and idempotent request keys prevent tampered browser amounts, duplicate active purchases and duplicate orders. A verified-email guest can use the same order flow without creating a User.

The eBook API and existing generic checkout API both enforce eBook readiness and **rzp_test_ only**. Changing existing commerce live flags cannot activate eBook live checkout. Callback uses original persisted provider order ID plus payment ID, constant-time HMAC and authenticated provider fetch; only captured matching amount/currency creates access. Existing webhook verifies raw body before parsing, persists event ID uniquely and reconciles provider state. Capture upserts one entitlement and one customer receipt job under callback/webhook races. Customer/admin emails are separate deduplicated jobs. Refunds use existing audited admin workflow and provider reconciliation; a verified full refund revokes access. Partial refunds remain recorded with existing access policy.

Register the existing HTTPS `/api/commerce/webhook` endpoint in the Razorpay **test** dashboard with the separate webhook secret. Subscribe to `payment.captured`, `payment.failed`, `refund.created`, `refund.processed`, `refund.failed`. `order.paid` is deliberately not consumed; captured payment events plus API reconciliation are authoritative. Use automatic capture as appropriate for the merchant account. Never point test and live dashboard configurations at interchangeable secrets. Settlement status is not used to grant buyer access.

Existing `/api/commerce/worker` retries payment/receipt jobs. Added `/api/ebooks/worker` reconciles one oldest test pending eBook order per run, rotates it for fairness, and processes access email/cleanup. Both require `Authorization: Bearer CRON_SECRET`. Vercel daily fallback is configured; production requires a more frequent authenticated scheduler if timely outage recovery is needed. Normal webhook/callback requests trigger background work immediately. Pending library orders can check provider status or resume the same order/request key.

Automated mocked tests cover capture, signature, amount/currency mismatch, concurrent duplicates, failure, refunds, private access and disabled/live gates. No real Razorpay order, captured test payment, dashboard registration or settlement was performed. Production switch remains blocked: explicit owner approval plus a separately reviewed release that removes the eBook test-only guard is required. Merely replacing environment credentials does not enable it.

Official references reviewed: [integration steps](https://razorpay.com/docs/payments/payment-gateway/web-integration/standard/integration-steps/) and [webhook validation/idempotency](https://razorpay.com/docs/webhooks/validate-test/).
